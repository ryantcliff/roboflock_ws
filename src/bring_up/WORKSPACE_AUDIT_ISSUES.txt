ROBOFLOCK ROS 2 WORKSPACE AUDIT
===============================

Audit date: 2026-08-27
Audited branch: dev (0f1722d)
Compared branch: main (7f38dc4)

SUMMARY
-------

The dev branch should remain capable of manual teleoperation when the system
service successfully runs bring_up/bring_up.sh, the expected joystick is
connected, and all four ODrives are available. However, hardware operation was
not tested during this audit.

The robot should initially be tested with its wheels raised. The present motor
control path has no stale-command watchdog. If joystick or ROS messages stop
while the robot is moving, an ODrive can retain its last requested velocity.

The integrated Nav2/beacon bring-up is currently broken and is not ready for an
autonomous field test.


BRANCH STATE
------------

1. dev is checked out and is 11 commits ahead of main.
2. main has no commits that are absent from dev; main is an ancestor of dev.
3. The only untracked workspace files during the audit were three frame PDFs.
4. dev adds or changes teleoperation, ODrive deceleration, twist_mux,
   localization, Nav2 parameters, and the top-level bring-up launch file.


CRITICAL PRIORITY
-----------------

1. No stale-command motor watchdog

   File: bring_up/diff_drive_controller.py

   The motor controller retains the last ODrive velocity until another Twist
   arrives or the node shuts down normally. If joy_node, the controller USB
   connection, the teleop node, or ROS communication fails while moving, the
   robot may continue moving.

   Required action: Add a motor-side timer that commands zero after roughly
   250-500 ms without a valid command. This must be independent of the joystick
   dead-man implementation.

2. dev top-level bring-up cannot launch

   File: launch/bringup.launch.py

   The nav2_node GroupAction definition is commented out, but the return value
   still schedules TimerAction(actions=[nav2_node]). Loading the launch file was
   confirmed to fail with:

       NameError: name 'nav2_node' is not defined

   Consequently, ros2 launch bring_up bringup.launch.py currently starts
   nothing.

3. Manual and autonomous velocity arbitration is disconnected

   Files:
     - bring_up/self_destruct.py
     - bring_up/diff_drive_controller.py
     - config/twist_mux.yaml
     - launch/bringup.launch.py

   twist_mux.yaml expects teleop on /cmd_vel_joy, Nav2 on /cmd_vel_nav, and mux
   output on /cmd_vel. In the current implementation, teleop publishes directly
   to /cmd_vel, the motor controller subscribes directly to /cmd_vel, standard
   Nav2 will normally publish /cmd_vel, and the mux launch is commented out.

   When Nav2 is enabled, manual commands will therefore not provide a reliable
   high-priority override. Competing publishers may command the motors directly.


HIGH PRIORITY
-------------

4. Teleop speed limits are dangerously high

   File: bring_up/self_destruct.py

   D-pad adjustment allows up to 10.0 m/s linear and 10.0 rad/s angular speed.
   With a 0.254 m wheel radius and 30:1 gearbox, 10 m/s requests approximately
   188 motor turns per second. The motor boundary has no independent saturation.

   Required action: Set conservative, measured teleop limits and clamp both
   manual and Nav2 commands again inside the motor controller.

5. The PS button can launch duplicate control stacks

   Files:
     - bring_up/self_destruct.py
     - bring_up/bring_up.sh

   Pressing PS launches bring_up.sh. That script starts another joy_node,
   self_destruct node, and diff_drive_controller. Repeated presses can create
   duplicate velocity publishers and competing ODrive connections.

   Required action: Remove this behavior or replace it with an idempotent,
   supervised mode/action mechanism. Do not press PS with the current stack.

6. Joystick disconnection is not handled safely

   File: bring_up/self_destruct.py

   Releasing R1 publishes zero only when a new Joy message arrives. A complete
   loss of Joy messages does not publish a stop. Button and axis arrays are also
   accessed without checking their lengths; a different controller mapping can
   crash the node.

7. Beacon coordinates do not share a defined Nav2 map datum

   File: beacon_pkg/src/beacon_goalpose.cpp

   The first beacon GPS fix becomes the origin. Subsequent UTM displacement is
   labeled directly as a pose in the map frame. This does not establish the
   transformation between beacon GPS, robot GPS, the SLAM map origin, and map
   orientation relative to UTM/true north. The first goal is effectively (0,0),
   independent of the robot's actual map position.

8. Beacon goal publication may not initiate navigation directly

   File: beacon_pkg/src/beacon_goalpose.cpp

   The beacon node publishes PoseStamped messages to /goal_pose. The dependable
   Nav2 programmatic interface is the NavigateToPose action. There is no explicit
   action client here, so the beacon node should not be assumed to initiate or
   update navigation without an RViz/plugin intermediary.

   A follower should use the action interface with goal replacement/cancellation,
   rate limiting, distance filtering, GPS validation, and a deliberate following
   distance instead of driving to the beacon's exact position.


MEDIUM PRIORITY
---------------

9. Inconsistent odometry topic names

   Files:
     - launch/localization.launch.py
     - config/nav2_params.yaml

   Localization publishes /odometry/local. MPPI uses /odometry/local, while
   bt_navigator is configured for /odom/local. No inspected launch file produces
   /odom/local.

10. Multiple nodes may compete for TF ownership

    Files:
      - config/ekf_navsat_params.yaml
      - config/slam_params.yaml

    Both EKFs have publish_tf enabled. SLAM Toolbox may also publish map->odom.
    The intended ownership should be exactly one source for each transform,
    normally local EKF for odom->base_link and either global localization or
    SLAM for map->odom. The live TF tree must be checked for duplicate publishers.

11. Beacon GPS data is not validated

    File: beacon_pkg/src/beacon_goalpose.cpp

    The callback does not reject invalid NavSatStatus, NaN coordinates, poor or
    unknown covariance, implausible GPS jumps, or UTM zone changes. A bad fix can
    immediately become a navigation goal.

12. Motor initialization can wait indefinitely

    File: bring_up/diff_drive_controller.py

    Four odrive.find_sync calls are performed sequentially without an apparent
    timeout. One missing ODrive can prevent startup from completing. The code also
    announces that a drive is enabled without verifying that the axis reached
    CLOSED_LOOP_CONTROL.

13. ODrive control gains are overwritten on startup

    File: bring_up/diff_drive_controller.py

    vel_gain and vel_integrator_gain are assigned for every drive each time the
    node starts. These values may be intentional, but they are not parameterized,
    validated per motor, or documented against measured tuning results.

14. Bash process cleanup is incomplete

    File: bring_up/bring_up.sh

    joy_node and self_destruct run in the background while the motor controller
    remains in the foreground. The script has no signal trap, PID tracking, or
    coordinated cleanup. Background processes may remain if the foreground node
    exits unexpectedly.

15. bring_up package dependencies are undeclared

    File: package.xml

    Runtime dependencies such as rclpy, geometry_msgs, sensor_msgs, joy,
    twist_mux, robot_localization, nav2_bringup, nmea_navsat_driver,
    robot_state_publisher, and the Python ODrive package are not declared. The
    workspace currently relies on these packages already existing on the system.


LOWER PRIORITY / REPOSITORY HYGIENE
-----------------------------------

16. urdf_description/launch/gazebo.launch.py contains mismatched brackets and
    fails Python compilation.

17. ultrasonic_pkg/params/ultrasonic_publisher.yaml uses invalid tab indentation
    and fails YAML parsing.

18. Editor backup files are committed, including #self_destruct.py#.

19. Several old motor-controller copies remain in bring_up/bring_up, making the
    authoritative implementation less obvious.

20. Test reporting found zero tests and a stale URDF_description versus
    urdf_description build artifact.

21. The installed workspace was produced by an earlier build. A clean, successful
    package build and launch-file validation should precede field testing.


MAIN VERSUS DEV
---------------

1. dev is the better base for manual operation.

2. main's bring_up.sh calls ros2 run bring_up self_destruct, but main does not
   register the self_destruct console entry point. Therefore its script does not
   provide a functional joystick-to-cmd_vel publisher as committed.

3. main's older motor controller implements nonstandard turning by stopping the
   inside wheels and multiplying the outside wheels by 1.5. dev uses conventional
   differential-drive kinematics and changes ramp rate for deceleration.

4. main defines its Nav2 group, but still lacks safe teleop/Nav2 arbitration and
   does not start the motor controller from the top-level launch.

5. Neither branch is presently ready for autonomous field use.


CURRENT TELEOPERATION VERDICT
-----------------------------

If the existing system service successfully calls bring_up/bring_up.sh after
reboot, dev is structurally capable of manual driving provided that:

  - the controller mapping still matches the configured PS4-style mapping;
  - /joy messages are being produced;
  - all four configured ODrive serial numbers are connected;
  - the installed ODrive Python API is compatible; and
  - cmd_vel messages reach diff_drive_controller.

Expected nodes include:

  /joy_node
  /ps4_teleop
  /diff_drive_controller

Controls documented in the current code:

  R1          Dead-man switch; hold to permit motion
  R2          Forward
  L2          Reverse
  Right stick Steering
  D-pad       Speed adjustment

Do not use the PS button with the current implementation. Perform the first test
with wheels raised and a physical emergency stop or power cutoff available.
